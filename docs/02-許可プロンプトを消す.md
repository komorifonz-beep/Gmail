# 02. 許可プロンプトを消す（本題）

上から順に試してください。上ほど安全で、上で解決すれば下は不要です。

前提として [`01-診断.md`](01-診断.md) の **A（ツール名の接頭辞）** が確定していること。

---

## 手0: ローカルの Claude Code にやらせる ← 一番ラク

JSON を自分で編集する必要はありません。**PC上の Claude Code は自分の `settings.json` を
書き換えられます。** デスクトップアプリを開いて、次をそのまま貼ってください。

```
~/.claude/settings.json の permissions に Gmail の MCP ツールを追加して。
既存の設定は消さずにマージすること。

allow（実際に接続されている Gmail サーバ名を調べて、その接頭辞で書く）:
  search_threads / get_thread / get_message / list_labels / list_drafts /
  create_draft / update_draft / label_thread

deny（サーバ名部分はワイルドカードで書く。例: mcp__*__delete_label）:
  apply_sensitive_message_label / apply_sensitive_thread_label /
  delete_label / unlabel_message / unlabel_thread

deny をワイルドカードにする理由: claude.ai コネクタのサーバ名は UUID で、
繋ぎ直すと変わる。allow が失効すれば許可プロンプトが戻るので気づけるが、
deny が失効すると黙って無防備になるため、deny だけは名前に依存させない。
```

[`01-診断.md`](01-診断.md) の **A（ツール名の接頭辞）** の確定も、この一言に含めてあります。
現物を見られる側に判断させるのが確実です。

**再起動は不要です。** `settings.json` の権限ルールは保存した時点で即座に反映されます
（実測で確認済み。検証方法は後述の「ルールが本当に効いているか確かめる」を参照）。
これで済んだ場合、下の手1・手2は不要です。

> クラウド側（Claude Code on the web）のセッションではこれはできません。
> 別マシンのコンテナで動いており、お手元の `settings.json` には届かないためです。

---

## 手1: 許可リストを設定ファイルに書く（自分で書く場合）

### やること

[`../settings/settings.example.json`](../settings/settings.example.json) の中身を
`~/.claude/settings.json` にマージします。

- macOS / Linux: `~/.claude/settings.json`
- Windows: `%USERPROFILE%\.claude\settings.json`

**すでに `settings.json` がある場合**は、丸ごと上書きせず `permissions.allow` と
`permissions.deny` の配列だけを足してください（他の設定を消さないため）。
ファイルが無ければ、サンプルをそのままコピーして構いません。

### 中身

`<SERVER>` は `/permissions` で確認した**実際のサーバ名**に置換してください。
claude.ai コネクタ経由の場合、ここは `Gmail` ではなく **UUID** になります。

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": [
      "mcp__<SERVER>__search_threads",
      "mcp__<SERVER>__get_thread",
      "mcp__<SERVER>__get_message",
      "mcp__<SERVER>__list_labels",
      "mcp__<SERVER>__list_drafts",
      "mcp__<SERVER>__create_draft",
      "mcp__<SERVER>__update_draft",
      "mcp__<SERVER>__label_thread"
    ],
    "deny": [
      "mcp__*__apply_sensitive_message_label",
      "mcp__*__apply_sensitive_thread_label",
      "mcp__*__delete_label",
      "mcp__*__unlabel_message",
      "mcp__*__unlabel_thread"
    ]
  }
}
```

### なぜ allow と deny で書き方が違うのか

**allow はサーバ名にワイルドカードを使えません。** グロブは `mcp__<server>__` の
**後ろ**にしか置けず、サーバ名部分はグロブ不可です（`mcp__*` のような書き方は allow では
無効で、警告が出て何も許可されません）。

**deny はグロブがツール名全体に一致すればよく、サーバ名部分も `*` にできます。**

この非対称性が、そのまま安全設計になります。

| | UUIDが変わったら | 気づけるか |
|---|---|---|
| `allow`（サーバ名を直書き） | 失効 → **許可プロンプトが戻る** | すぐ気づく（安全側の壊れ方） |
| `deny`（`mcp__*__` で記述） | **効き続ける** | そもそも壊れない |

claude.ai コネクタを一度外して繋ぎ直すと UUID が変わります。もし deny もサーバ名を
直書きしていると、**黙って無防備になる**（防げたつもりで防げていない）。
そのため deny だけはサーバ名に依存させません。

> 許可プロンプトが急に戻ってきたら、まず「コネクタを繋ぎ直して UUID が変わった」を疑い、
> `/permissions` で現在のサーバ名を確認して allow を書き直してください。

### `deny` に何を入れてあるか

| ツール | 何をするか |
|---|---|
| `apply_sensitive_message_label` / `apply_sensitive_thread_label` | ゴミ箱・迷惑メールに移す |
| `unlabel_message` / `unlabel_thread` | INBOX ラベルを剥がす＝**アーカイブ相当** |
| `delete_label` | ラベルそのものを削除 |

いずれも無人実行で発動すると取り返しがつきにくい操作です。仕分けプロンプトは
これらを一切使わないので、塞いでも動作に影響しません。
`deny` は `allow` より強いので、うっかり allow に混ざっても発動しません。

### 確認

設定を保存したら、そのまま仕分けを実行します（**再起動は不要**）。
一度もプロンプトが出なければ完了です。

---

## ルールが本当に効いているか確かめる

`*` を含むルールは**起動時のtypo警告の対象外**です（「Tool names containing `_` or `*`
are exempt from the check」）。つまり綴りを間違えても黙って無効になります。
`deny` の綴りミスは「防げたつもりで防げていない」状態を生むので、実測で確かめます。

### 方法: 無害な読み取り専用ツールを一時的に deny して踏む

1. `deny` に一時的に1行足す

   ```json
   "mcp__*__list_labels"
   ```

2. Claude に「Gmailのラベル一覧を出して」と頼む
3. **拒否されれば成功。** 次の3つが同時に証明されます
   - 中間位置グロブ `mcp__*__<ツール名>` がサーバ名セグメント（UUID）を跨いで一致する
   - `deny` が `allow` に勝つ（`list_labels` は allow にも入っているのに拒否される）
   - 権限ルールが**再起動なしで即時反映**される
4. 一時行を消す → もう一度頼んで通ることを確認して撤去完了

`list_labels` は読み取り専用なので、この検証で壊れるものはありません。

> 5行すべてを個別に実測する必要はありません。1本通れば「同じ形状のグロブが機能する」
> ことは示せます。残りは**綴りが実在ツール名と一致しているか**だけを目視で確認してください。

## 手2: `/permissions` から追加する

JSON を手で書きたくない場合。Claude Code で:

```
/permissions
```

からルールを追加できます。あるいは**許可プロンプトが出たときに
「Yes, don't ask again」を選ぶ**のでも同じ効果です（設定ファイルに書き込まれます）。

手1と結果は同じなので、やりやすい方でどうぞ。

---

## 手3: それでも毎回聞かれる場合

許可リストを正しく書いたのにプロンプトが出続けるなら、**許可ルールでは消せない種類**の
ツールに当たっています。次のどちらかです。

- 組織が `ask` に設定した claude.ai コネクタのツール
- MCP 側で `requiresUserInteraction` が指定されているツール

このどちらかだと、`--permission-mode bypassPermissions` にしても**プロンプトは出ます**
（`dontAsk` にすると逆に拒否されて動きません）。設定では回避できません。

### 対処: 送信・下書き部分を Claude の外に出す

判断は Claude にさせ、**Gmail への書き込みは素のスクリプトにやらせる**構成に変えます。
レイバー資料メールが黙って動いているのと同じ形にする、ということです。

```
[Claude] 受信メールを読んで仕分け → 結果を JSON でファイルに書き出すだけ
                                              ↓
[Pythonスクリプト] JSON を読んで Gmail API / SMTP で下書き作成＋レポート送信
```

Claude 側は読み取り系ツール（`search_threads` / `get_thread`）とファイル書き込みだけに
なるので、承認を求める箇所が消えます。書き込み系は [`01-診断.md`](01-診断.md) の **C** で
見つけたレイバー資料スクリプトの SMTP 部分をそのまま流用できます。

この構成に切り替える場合は、診断結果（特に C のスクリプトの中身）を持ってきてください。
スクリプトを書き起こします。

---

## 手4: `--dangerously-skip-permissions` ← 薦めません

全プロンプトを素通しにするフラグです。**メール操作の権限を持ったセッションを
無条件で走らせる**という意味になるので、ここでは使わないでください。
手1〜3 で解決します。

（そもそも手3のケースでは、このフラグを使ってもプロンプトは消えません。）
