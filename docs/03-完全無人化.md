# 03. 完全無人化 — 手動起動そのものを無くす（第2段階）

[`02-許可プロンプトを消す.md`](02-許可プロンプトを消す.md) でプロンプトが消えたら、
次は起動もスケジューラに任せます。ここまでやると、レイバー資料メールと完全に同じ
「気づいたら届いている」状態になります。

---

## 最短ルート: 既存の送信スクリプトに乗せる（推奨）

実機調査で分かった現状はこうです。

- スケジュールタスクは9本あるが、**`claude.exe` を叩くものは1本もない**（全て python）
- `MorningTriageMailer` は**毎日 8:10 JST のトリガーを持っている**
- レポート本文のファイルが更新されるのは 11:56 頃、mailer の実行は 13:12
- レイバー資料の送信は毎日 7:37 JST ±90秒で安定して走っている

つまり**送信の仕組みはすでに完成していて、動いています**。欠けているのは
「8:10 のmailerが走る時点で、まだレポート本文が出来ていない」という一点だけです。
人が Claude を回すのが 11時頃なので、8:10 には読むものが無い。

だったら**Claude を mailer より前に走らせるだけ**で終わります。送信スクリプトは
1行も触りません。

### 目標の時刻

レイバー資料が毎日 **7:37 JST** に届くので、仕分けレポートはその少し前に着かせます。

```
07:20 JST  claude -p でレポート生成 → ファイルに書き出す
           ↓ 成功したときだけ
           既存の送信スクリプトを呼ぶ → Gmail へ送信
07:37 JST  レイバー資料（既存・変更なし）
```

朝の2通がまとまって届きます。

### 2本のタイマーではなく、1本にまとめて連結する

「Claude を 7:20、mailer を 7:30」と別々のタイマーにするのは避けてください。
Claude の実行が10分を超えた日に、**mailer が前日のレポートを送ります**。
静かに間違ったものが届くので、事故に気づけません。

1本のタスクの中で `&&` で繋ぎます。

```bat
claude -p ... > "<mailerが読むファイル>" && <既存の送信コマンド>
```

`&&` なので、Claude が失敗した日は送信されません。**古いレポートが送られる事故が
構造的に起きなくなります**（届かなければ気づけますが、間違ったものが届くと気づけません）。

連結が動いたら、既存の `MorningTriageMailer` の **8:10 トリガーは無効化**してください。
残すと二重送信になります。

### レポートは送信、返信は下書き

- **レポート** → 送信まで到達させる（既存スクリプトが担当）
- **相手への返信** → 下書きのまま。本人が確認してから送信

プロンプト側で `create_draft` を使うのは返信下書きだけです。レポートの下書きは
作りません（送信経路が二重になり、下書きが毎日溜まるため）。

### 唯一の未確定: mailer が読むファイル

これだけが分かれば完成します。**本人も把握していない**ので、次の順に特定します。

1. **タスク定義の Actions を丸ごと見る。** `MorningTriageMailer` の `Execute` と
   `Arguments` を省略せず出力します。ファイルパスが引数に入っていることがよくあります。

   ```powershell
   (Get-ScheduledTask -TaskName MorningTriageMailer).Actions |
     Format-List Execute, Arguments, WorkingDirectory
   ```

2. **候補ファイルを絞る。** スクリプトと同じフォルダを一覧し、更新時刻を見ます
   （中身は読みません。`Get-ChildItem` の一覧・タイムスタンプだけ）。
   送信時刻の直前に更新されている `.txt` が候補です。

3. **1通だけ実測して確定させる。** 候補ファイルに `TEST-<ランダムな文字列>` の1行を書き、
   mailer を手で起動して、その文字列が届いたメールに入っているか見ます。
   入っていればそれが正解のファイルです。届くのは自分宛の1通だけなので、
   確認後に消せば元に戻ります。

   > 元の中身は先に控えて、テスト後に書き戻してください。

**`.claude/secrets/` の中身は読まないこと。** 本人が意図して設けたガードです。
上の3手順は、ファイルの一覧・タイムスタンプ・実測だけで完結し、中身を読まずに特定できます。
どうしても特定できなければ、本人に `send-email.py` を開いてもらい、
読み込み先のパスが書かれた行だけを教えてもらってください。

## 考え方

対話モードで起動するから許可を聞かれます。**`-p`（print モード）は非対話**なので、
そもそも聞く相手が居ません。加えて `--allowedTools` はコマンドライン引数なので、
設定ファイルより優先されます（優先順位は Managed > **コマンドライン引数** > local >
project > user）。つまりこの1行だけで、設定ファイルの状態に関係なく無人で走ります。

## 基本コマンド

```bash
claude -p "$(cat prompt/朝のメール仕分け.md)" \
  --allowedTools "mcp__<SERVER>__search_threads,mcp__<SERVER>__get_thread,mcp__<SERVER>__get_message,mcp__<SERVER>__list_labels,mcp__<SERVER>__list_drafts,mcp__<SERVER>__create_draft" \
  --disallowedTools "mcp__*__apply_sensitive_message_label,mcp__*__apply_sensitive_thread_label,mcp__*__delete_label,mcp__*__unlabel_message,mcp__*__unlabel_thread" \
  --model claude-sonnet-5 \
  --max-turns 30
```

| フラグ | 役割 |
|---|---|
| `-p` | 非対話モード。プロンプトが出ない |
| `--allowedTools` | 事前承認するツール。設定ファイルより優先 |
| `--disallowedTools` | ゴミ箱／迷惑メール操作を禁止する安全弁 |
| `--max-turns 30` | 想定外に長引いたら止める安全弁 |

> `<SERVER>` は `/permissions` で確認した実際のサーバ名に置換してください。
> claude.ai コネクタ経由の場合は **UUID** になります（[`01-診断.md`](01-診断.md) の A）。
> `--allowedTools` はサーバ名を直書きするしかありませんが、`--disallowedTools` は
> `mcp__*__` のワイルドカードで書けるので、UUIDが変わっても効き続けます。
> なお `settings.json` の `deny` が主たる防壁で、こちらは二重の保険です。

## Windows（タスクスケジューラ）

### 1. 起動用バッチを作る

`D:\scripts\asa_mail_shiwake.bat`（パスは環境に合わせて）:

レポート本文を**ファイルに書き出し、成功したときだけ**既存の送信スクリプトを呼びます。
失敗したら**0以外で終了**します。これがWindowsのリトライの引き金になります。

```bat
@echo off
setlocal enabledelayedexpansion
cd /d D:\scripts\Gmail

rem ファイル名は ASCII のみにすること（バッチのコードページ事故を避ける）
set "PROMPT=%~dp0prompt_asa_shiwake.md"
set "REPORT=C:\Users\user\claude-reports\line-report.txt"
set "TMPOUT=%~dp0logs\report_new.txt"
set "LOG=%~dp0logs\shiwake.log"
set "DONE=%~dp0logs\shiwake_done.txt"

for /f %%d in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd"') do set "TODAY=%%d"

rem === 今日ぶんが完了済みなら何もしない（リトライによる二重送信の防止）===
if exist "%DONE%" (
  set /p LAST=<"%DONE%"
  if "!LAST!"=="%TODAY%" (
    echo [%TODAY%] already sent - skip >> "%LOG%"
    exit /b 0
  )
)

rem === レポート生成（本番ファイルには直接書かない）===
type "%PROMPT%" | claude -p ^
  --allowedTools "mcp__<SERVER>__search_threads,mcp__<SERVER>__get_thread,mcp__<SERVER>__get_message,mcp__<SERVER>__list_labels,mcp__<SERVER>__list_drafts,mcp__<SERVER>__create_draft" ^
  --disallowedTools "mcp__*__apply_sensitive_message_label,mcp__*__apply_sensitive_thread_label,mcp__*__delete_label,mcp__*__unlabel_message,mcp__*__unlabel_thread" ^
  --model claude-sonnet-5 ^
  --max-turns 30 ^
  > "%TMPOUT%" 2>> "%LOG%"

if errorlevel 1 (
  echo [%TODAY%] claude failed - will retry >> "%LOG%"
  exit /b 1
)

rem === 中身の検証（rc=0 でも空・拒否メッセージのことがある）===
for %%f in ("%TMPOUT%") do set "SIZE=%%~zf"
if !SIZE! LSS 300 (
  echo [%TODAY%] output too small ^(!SIZE! bytes^) - will retry >> "%LOG%"
  exit /b 1
)

copy /y "%TMPOUT%" "%REPORT%" >nul

rem === 送信（pythonw ではなく python。終了コードを拾うため）===
python.exe "<send-email.py のフルパス>" >> "%LOG%" 2>&1

if errorlevel 1 (
  echo [%TODAY%] send failed - will retry >> "%LOG%"
  exit /b 1
)

rem === 完了マーク ===
> "%DONE%" echo %TODAY%
echo [%TODAY%] done >> "%LOG%"
exit /b 0
```

### 実機で判明した、雛形が踏んでいた地雷

以下は実際に組んで見つかったものです。同じ形で書くときは全部避けてください。

| やりがちな書き方 | 何が起きるか | 正しい書き方 |
|---|---|---|
| `claude -p "path\to\prompt.md"` | **パス文字列がプロンプトとして渡る**。中身は読まれない | `type "%PROMPT%" \| claude -p` |
| `pythonw.exe` で送信 | コンソールから切り離され、**終了コードが拾えない**＝リトライが発火しない | `python.exe` |
| `> "%REPORT%"` で本番ファイルに直接生成 | 失敗した日に**本番ファイルが空で残る** | 一時ファイル→検証→コピー |
| 終了コードだけ見る | `rc=0` でも**空出力**の日があり、空メールが飛ぶ | **300バイト**未満なら失敗扱い |
| プロンプトを日本語ファイル名で置く | バッチのコードページ次第で読めない | ASCII名にリネーム |
| `--allowedTools` に `label_thread` | 不要。ラベルは**Gmail側のフィルタ**が付けている | 外す |

### 同じコネクタが、ホストによって別の名前で載ります（最重要の落とし穴）

実機で確定した事実です。**まったく同じ Gmail コネクタが、実行環境によって別のサーバ名を持ちます。**

| 実行環境 | サーバ名 |
|---|---|
| デスクトップアプリ／SDKセッション | `mcp__5f34db31-7993-4baa-9531-07c8fe67dabd__`（UUID） |
| `claude.exe`（CLI・ヘッドレス） | `mcp__claude_ai_Gmail__` |

つまり**デスクトップで確認した名前を、そのままヘッドレス実行に持ち込むと落ちます。**
`claude mcp list` は `√ Connected` と出るのに、`mcp__` ツールが1つも載らない、
という分かりにくい形で失敗します。

**必ずヘッドレス側で実測してください。** デスクトップの `/permissions` で見た名前は、
デスクトップ用です。

そしてここが `deny` をワイルドカードにしておいた効果が出た場面です。

- `deny`（`mcp__*__...`）… **両方の名前を自動でカバーした。** 何もしなくても効き続けた
- `allow`（サーバ名直書き）… CLI側の名前で書き直しが必要だった

UUIDローテーション対策として入れたものが、想定していなかった「二重名前空間」でも
そのまま機能しました。`deny` は名前に依存させない、という判断が二重に効いています。

### 件名とラベルは Claude の担当ではありません（実測で確認）

- **件名** … `send-email.py` が生成しています。ファイルの中身には含まれません。
  つまり件名は常に正しく、**ズレ得るのは Claude が書く本文側だけ**です。
  プロンプトで D を先に固定しているのは、まさにここに効いています。
- **`5,メール仕分け` ラベル** … Gmail 側のフィルタが自動付与しています。
  Claude の `label_thread` ではありません。だから `--allowedTools` から外せます。

### 設計のポイント

**完了マーク（`shiwake_done.txt`）が要になります。** リトライを入れる以上、
「送信は成功したが、後続の何かで0以外を返した」ケースで**同じ日に2通送る**事故が
起きえます。日付を書いたマークファイルを見て、その日ぶんが済んでいれば即座に
`exit /b 0` で抜けます。リトライは何度発火しても、送信は1日1回に固定されます。

**`if errorlevel 1` で止めています。** Claude が失敗した日は送信しません。
ここを繋ぐと、失敗した日に前日のレポートがそのまま送られます。
届かなければ気づけますが、間違ったものが届くと気づけません。

**返信下書きの重複は、プロンプト側の手順3が防ぎます。** リトライで Claude が
2回走っても、`list_drafts` で既に下書きのあるスレッドを飛ばすので、
同じ相手に2通の下書きは作られません。

**サイズ判定は 300 バイトです。100 では足りません。** `rc=0` で返る失敗出力には
中身があります。実測では**拒否メッセージが 108 バイト**あり、100バイト判定を
すり抜けました。正常なレポートは約 1KB あるので、300 なら両者を確実に分けられます。

**検索窓は `newer_than:30h` です（`1d` ではありません）。** リトライで実行時刻が
最大5時間ずれると、`1d` では前回実行との間に**隙間**が空きます。

```
8/11 07:20 実行 … 8/10 07:20 〜 8/11 07:20 をカバー
8/12 07:20 失敗 → 12:20 に成功 … 8/11 12:20 〜 8/12 12:20 をカバー
                                  ↑ 8/11 07:20〜12:20 が誰にも見られない
```

`30h` にすると通常日は6時間ぶん重複しますが、**重複は「同じ件が翌日にも載る」だけで
気づけます。隙間は取りこぼしたこと自体に誰も気づけません。** 重複側に倒しています。

> `-p` にファイルパスを直接渡せない場合は、`claude -p "%PROMPT%"` の形で
> いったん変数に読み込んでください（PowerShell なら `Get-Content -Raw`）。

> ログを `>>` でレポートと同じファイルに混ぜないこと。レポートは `>`（上書き）で
> 書き、ログは別ファイルへ `2>>` で分けます。混ざるとメール本文にログが載ります。

### 2. タスクとして登録

```powershell
$action   = New-ScheduledTaskAction -Execute "D:\scripts\asa_mail_shiwake.bat"
$trigger  = New-ScheduledTaskTrigger -Daily -At 7:20am
$settings = New-ScheduledTaskSettingsSet `
              -StartWhenAvailable `
              -WakeToRun `
              -AllowStartIfOnBatteries `
              -DontStopIfGoingOnBatteries `
              -RestartInterval (New-TimeSpan -Hours 1) `
              -RestartCount 5 `
              -ExecutionTimeLimit (New-TimeSpan -Minutes 30)
Register-ScheduledTask -TaskName "朝のメール仕分け" -Action $action -Trigger $trigger `
  -Settings $settings `
  -Description "Gmail の要返信を仕分けして返信下書きを作成し、レポートを自分宛に送信"
```

**7:20 にしてある理由**: レイバー資料が 7:37 JST に届くので、その少し前に着かせて
朝の2通をまとめています。

### 「送れなかった」の2種類と、それぞれの保険

移動中などで朝に送れないケースは、Windows的には**別々の事象**です。設定箇所も違うので、
両方入れないと片方しか救えません。

| 何が起きたか | 例 | 効く設定 |
|---|---|---|
| **そもそも走らなかった** | 7:20にPCがスリープ／電源オフ | `-StartWhenAvailable`（＋`-WakeToRun`） |
| **走ったが失敗した** | ネット未接続、APIエラー、ログイン切れ | `-RestartInterval 1h` `-RestartCount 5` |

- `-StartWhenAvailable` … 予定時刻を過ぎていたら、**PCが使える状態になった時点で実行**します。
  これが無いと、7:20に止まっていた日はエラーも残さず静かにスキップされます（Windowsの既定）。
  なお実行は「利用可能になってから10分程度以内」で、即座ではありません。
- `-WakeToRun` … スリープからは起こして実行します。**電源が落ちていれば起きません。**
- `-RestartInterval` / `-RestartCount` … タスクが**0以外で終了したとき**に、1時間おきに
  最大5回やり直します。7:20開始なら 12:20 頃までが守備範囲です。
- `-ExecutionTimeLimit` … 30分で打ち切ります。これが無いと、ハングした実行が居座って
  リトライも次の日の実行も始まりません。
- `-AllowStartIfOnBatteries` / `-DontStopIfGoingOnBatteries` … **これが最重要です。**
  `New-ScheduledTaskSettingsSet` は既定で「AC電源のときだけ実行する」になっており、
  指定しないと**バッテリー駆動の朝は静かにスキップされます**。保険が要る日
  （移動中・外出先）にだけ効かない設定になるので、必ず両方入れてください。

リトライが何度発火しても、バッチ冒頭の完了マーク判定により**送信は1日1回**です。

> GUIで作る場合: リトライは「設定」タブの
> 「タスクが失敗した場合の再起動の間隔」＋「再起動試行回数」、
> 取りこぼし対策は同じ「設定」タブの
> 「スケジュールされた開始時刻を過ぎた場合、すぐにタスクを開始する」、
> スリープ解除は「条件」タブです。

### 3. それでも届かない日はある

上の設定でも、**PCの電源が落ちたまま一日中使わなければ動きません。**
`-WakeToRun` はスリープからは起こせますが、電源オフからは起動できないためです。

その日が許容できないなら、クラウド版を併用する話になります（レポートは
完了通知メール＋Pushでの配信になり、SENTには残りません）。
いまの構成では「PCを一度も開かない日は届かない」を許容する設計です。

### 4. 「走ったのに何もしなかった」を見分ける

`MorningTriageMailer` の「前回の実行時刻」が手動実行の時刻になっていても、
**定時に走っていないとは限りません**。手動実行が記録を上書きするためです。
定時トリガーが発火したかどうかは、タスクスケジューラの**「履歴」タブ**、または
イベントビューアの `Microsoft-Windows-TaskScheduler/Operational` で確認してください。

「定時に走ったが、読むべきレポートがまだ無くて何もせず終了した」と
「そもそも走っていない」は、打つ手が違います。前者なら Claude を前倒しするだけで
解決し、後者ならタスク設定（上の2つ）の問題です。

## 認証（ここで一度つまずきます）

### デスクトップアプリが動いていても、`claude.exe` は未認証のことがあります

デスクトップアプリのセッションは別経路の資格情報で動いており、**コマンドラインの
`claude.exe` はそれを共有しません**。実機では `claude -p "Reply with exactly: OK"`
すら `Not logged in · Please run /login` を返しました
（`.credentials.json` が 238B・36日前のまま）。

対処は、**対話ターミナルから通常の `/login`** です。

```
claude
```

を起動して `/login`、完了後に `/status` の `Login` 行を確認してください。
これで `.credentials.json` が更新され、ヘッドレス実行もコネクタごと引き継ぎます。

### `claude setup-token` は使わないこと（この構成では壊れます）

無人実行の定番として `claude setup-token` で1年トークンを発行し
`CLAUDE_CODE_OAUTH_TOKEN` に設定する方法がありますが、**この構成では採ってはいけません。**

公式ドキュメントに明記があります。

> It can only make model requests, so it can't establish Remote Control sessions or
> **fetch claude.ai connectors**. MCP servers you configure locally still work.

ここでの Gmail は **claude.ai コネクタ**（サーバ名がUUID）です。ローカル定義のMCPでは
ないので「locally still work」の救済に入りません。結果として:

- 認証は通る（モデル呼び出しは成功する）
- **Gmail ツールだけが存在しなくなる**
- 認証エラーではなく「ツールが無い」という形で失敗する

という、原因を追いにくい壊れ方をします。**通常の `/login` を使ってください。**

### ログイン切れの監視

無人実行では、ログインが切れると黙って止まります。Claude Code は期限の3日前から
起動時に警告を出しますが、無人実行だと誰も読みません。

- 対話で Claude Code を開いたとき、`/status` の `Login` 行をときどき見る
- レポートが届かない日が出たら、まずここを疑う（`logs\shiwake.log` に
  `Not logged in` が残ります）

この構成では「届かなければ気づける」ので、監視はこれで足ります。
